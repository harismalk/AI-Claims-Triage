| 2026-11-01 | T3.2: the golden-set test (`test_handles_same_date_different_procedure_edge_case_on_the_golden_set`) caught a real bug in the duplicate-denial specialist's first implementation before anything was marked done. `default_reason_fn` picked the first claim in `find_similar_claims`'s result list sharing the disputed claim's procedure code — but that tool matches on `(same proc_cd OR same visit_id)`, so for dispute 131 it returned an unrelated background claim that coincidentally shared the procedure code, ahead of the actual flagged counterpart (the claim sharing the disputed claim's `VISIT_ID`). | 2026-11-01 | T3.3: testing the billing-error specialist against the real T1.3 answer key surfaced a genuine bug in `app.generate_data._plant_bil_claim` (T1.3, already marked done): `_plan_copay_cents(...) or 2_000` used Python's `or`, which treats `0` as falsy, so for every plan/service-type combo with a genuinely defined $0 copay (HDHP_2000's entire schedule, and `preventive_care` on every plan) the generator silently substituted a $20 baseline instead of the real $0 — producing wrong ground truth: `denial_correct` BIL disputes on HDHP_2000 were actually $20 overcharges mislabeled as correctly-charged, and `should_reverse` overage amounts were inflated by the same $20. | 2026-11-01 | T4.5: before trusting the updated `.github/workflows/ci.yml`, ran the exact same command sequence locally against a genuinely fresh, empty Postgres container (`docker run postgres:16` with no init scripts, simulating the GitHub Actions service container precisely) rather than the already-initialized local `docker-compose` instance. | 2026-11-01 | T5.1: building the first real executor (the accept/override API endpoint, calling `update_claim_status`, `issue_adjustment`, and `resolve_dispute` together to resolve one dispute) surfaced a real idempotency bug in `app.legacy_api.call_legacy_api` (T2.2, already marked done). `LGCY_REQ_LOG`'s idempotency cache was keyed on the bare `RequestKey` alone, with no scoping by request type. T2.2's own tests never caught this because they only ever retried the SAME operation under the SAME key — but resolving one dispute legitimately shares one `request_key` across three DIFFERENT operations. Verified empirically: calling `update_claim_status` then `issue_adjustment` with the same key caused the second call to silently short-circuit as "replayed" and never actually apply (the claim's `paid_amount_cents` didn't change). The bug was introduced by `app/api.py`'s own first draft, which reused one bare key across all three calls. | Helped (caught before it shipped) | Fixed at the root in `call_legacy_api` — the cache key is now `"<request-tag>:<RequestKey>"`, protecting every caller rather than requiring each call site to manually namespace keys. Added `test_different_request_types_sharing_one_request_key_do_not_collide`; confirmed the original single-operation-retry test still passes unchanged. |
